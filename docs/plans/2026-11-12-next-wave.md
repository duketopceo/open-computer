# Next wave - Plan

**Source:** Luke, 2026-11-12 (chat UI, OpenRouter SDK, Settings, Cloudflare, one-line setup, web access, subagent routing, self-host and distribution), with a 2026-11-13 follow-up that the five-click Tauri path is the main way a new person starts, and that High, routing, and Gemini 4 Hydrogen are decided. Verified against `main` at `af3be15` ( [#160](https://github.com/duketopceo/open-computer/pull/160) and [#161](https://github.com/duketopceo/open-computer/pull/161) are merged). New UI must not reintroduce violet or composer sentences. Model-catalog and routing work is in [#163](https://github.com/duketopceo/open-computer/pull/163) and is recorded here, not re-implemented.

This is a plan only. No feature code in this PR, except a test isolation fix noted under Verification.

## Summary

Ship the next slice of the everyday chat product as a sequence of small, tested PRs: streamed words with a subtle reveal, live collapsible reasoning, slightly differentiated action buttons, a finished Settings page, a five-click desktop setup (the main path for a new person), a near one-click Cloudflare path from Settings, web search that works from a single OpenRouter key, and OpenCode-style named subagents on top of the existing orchestrator. Developers still get `curl | sh` or `docker compose up`. Do not rewrite the UI in Rust, do not move the app database to Cloudflare D1, and do not add a browser-side OpenRouter SDK.

## Problem frame

Luke asked for a status pass and then a set of product pieces, including how a new person would stand up Cloudflare, a backend (Docker or a VM), wrangler, a localhost mode, a possible Rust GUI that stays in sync with the web page, login, and where data lives (D1, R2, or a database in the container). Several of those already exist in part on `main`. The gaps that a person would notice first are: replies still arrive all at once, reasoning is only shown after a run finishes (and only on the run card, or in dev-mode call rows), the composer has no Stop / copy / retry chrome, Settings is a short stack of partial sections, and there is no five-click installer — the README still says "No package or CLI yet." The main setup path is a Tauri desktop app from GitHub Releases that starts a bundled Python backend and a localhost portal, not a Docker-first install.

## OpenCode recommendation

Yes for the **agent model**, no for replacing Open Computer's shell with OpenCode.

OpenCode (as of its 2026 agents docs) gives each named agent a mode (`primary` / `subagent` / `all`), a model, a system prompt, and a permission list; the primary can launch subagents, and the user can `@mention` one. That is the right shape for OC's product layer: a chat orchestrator that hands work to a small set of specialists (research, code, browse), each with its own OpenRouter model, tools, and permissions, under the parent turn's budget.

Do **not** make OpenCode the product. OC already wraps OpenCode as the coding harness (`ori opencode acp`) and should keep it there. @-mention in OC should **deterministically** spawn the named agent (OpenCode's mention is only a suggestion to the model, which has surprised people). Depth stays 1. The effort concurrency cap (Low 0, Medium 2, High 4, from the chat-agent product plan) applies to **orchestrator-initiated** spawns: at Low the orchestrator does not start a subagent on its own. An explicit `@name` is a user action and always spawns that agent, including at Low (the default effort). Multiple explicit mentions at Low run one at a time; Medium and High keep their concurrent caps, and mentions count toward them.

Routing optimizations to land with that work: native tool calling for the chat orchestrator (daily-driver U6, still unbuilt); wire or retire the unwired `AgentLoop` production path; keep the #159 "no second classify" rule; log spawn rate and cost so over-use is visible; do not add a second router on the goal path.

## Key technical decisions

- **KTD1. Streaming is SSE on the existing stdlib server, through the official Python SDK.** Follow daily-driver KTD3 and U2: `chat_stream` on `services/openrouter/client.py` uses the SDK's streaming chat API (not a second urllib SSE client); events `message.delta`, `reasoning.delta`, `message.done`, `run.state`, `turn.done`, `turn.error`; `Last-Event-ID` resume; `GET /api/threads/<id>` polling remains the fallback. Reveal animates only newly appended words. This unit *is* the "add the rest of the first-party SDK" work that matters; there is no separate "add `@openrouter/sdk` to the SPA" PR (R4).
- **KTD2. Reasoning is a first-class chat surface, collapsible, requested on Medium/High.** Extend `collect_reasoning` to the chat orchestrator path, not only `services/orchestrator/runner.py`. Live tokens use `reasoning.delta`. Before any reasoning text is written to the event log (or any other disk), run the same `redact_str` and size cap as `services/orchestrator/thinking.py`, against a rolling buffer of the stream — not each delta in isolation — so a secret split across chunks is still caught. The existing post-hoc Thinking block on `RunView` stays for completed steps. Dev-mode `CallRow` stays dev-mode.
- **KTD3. "Web access for the frontend" is two jobs, not one feature.** (1) Reach the app from a browser on the internet: U5+U6 (localhost always, Cloudflare optional). (2) Let the chat use the web: keep `web.search` / `web.fetch` and the Sources panel; default search to Sonar when an OpenRouter key is present and no other provider is set, so a one-line install gets web search without a second API key. Do not build a parallel "web access" feature.
- **KTD4. The main setup path is a five-click Tauri desktop app with a bundled Python backend. `curl | sh` and Docker Compose stay the developer path.** For a new person: (1) download the app from GitHub Releases, (2) open it — it starts a bundled Python opsview as a single built-in program (a frozen sidecar, not a Docker daemon) on `127.0.0.1:8791` and opens the localhost portal, (3) sign in with the existing OpenRouter OAuth, (4) optionally flip "Put this online" in Settings, (5) chat. Docker is not required. The developer path remains `scripts/install.sh` and `deploy/localhost/docker-compose.yml`: same image family as `deploy/server-001/Dockerfile`, opsview only, `OC_DURABLE=0`, bind `127.0.0.1:8791`, volume for `OC_ROOT`. Temporal+Postgres is an optional `--durable` profile. Document `curl | sh` from a pinned release tag *and* `docker compose` from a checkout. "Or a VM" means: install Docker on the VM, run the same compose; a custom cloud image is out of scope for this wave.
- **KTD5. "Put this online" in Settings runs the same wrangler- and cloudflared-driven flow as the setup script; it is not fully unattended.** See [Self-host and distribution](#self-host-and-distribution). The toggle starts login, Tunnel create, local config, and the supervised `cloudflared` process (see [Self-host (a)](#a-near-one-click-cloudflare)); it still prints the CNAME and Access steps a human must finish. Startup failures are shown in Settings; the process stops when the toggle is off or the app quits, and starts again on the next launch if the toggle is still on. A "Deploy to Cloudflare" button can publish the *static demo* Worker; it cannot finish DNS or an Access policy on its own. The backend stays on the person's machine (bundled process or Docker), Tunnel to loopback, Access in front, same-origin (the 2026-11-01 frontend plan). Do not move the Python backend onto Workers in this wave.
- **KTD6. The desktop app is Tauri wrapping `ui/`, with a bundled Python backend, in this wave — the main setup path, not a later extra.** Not a Rust rewrite of chat or the orchestrator. The window and the browser load the same UI and call the same opsview and the same account session. Sync is that shared API, not a second replica or a CRDT. If the desktop's local opsview and a browser pointed at a different host are two instances, say so in the UI rather than pretending they merge.
- **KTD7. Auth does not grow a password system.** Keep loopback `local_session` (no ceremony; `services/opsview/auth.py`), passkeys for a host that is not loopback and not behind Access, and Access-minted sessions when the perimeter already authenticated the person. Localhost compose uses the local session. Internet exposure requires Access (and/or passkeys) — the install script must not publish `0.0.0.0` without saying so. For self-host, `OC_ACCESS_IDENTITY_URL` is required when Access is enabled and has no baked team default.
- **KTD8. Application state stays files on the `oc-data` volume for this wave. Next database, if we outgrow files, is SQLite in the container. D1 is not the app DB. R2 is optional object storage for large artifacts when Cloudflare-hosted.** See [Self-host and distribution](#self-host-and-distribution) item (f). Temporal's Postgres remains only Temporal's.
- **KTD9. Named agents are repo- and user-config on the OC orchestrator, OpenCode-esque, depth 1.** Config shape can follow OpenCode's (name, description, mode, model, tools, permissions) so the idea is familiar, stored in OC (for example `docs` or a host file under `OC_ROOT`), not by asking the person to run OpenCode as their chat. `@name` in the composer is a hard spawn, including at Low effort, tested as such. Low's zero-subagent cap is for orchestrator-initiated spawns only; an unsolicited spawn at Low is rejected with a clear explanation. The coding specialist may still launch the existing ACP OpenCode worker.
- **KTD10. Settings stays one page of sections** (accounts-plan KTD7). New sections are components under `ui/src/pages/settings/`. Lane keys: show connected / missing / shared-fallback per lane, never the secret, never a paste-into-the-browser field (env and omaseal stay the store; OpenRouter OAuth continues to create the shared key). Daily cap: display spend vs cap; raising the host cap from the UI is a later decision (Open question Q1) — until then the section explains `OC_DAILY_CAP` and shows live numbers.
- **KTD11. Tests never call a live model, a live Cloudflare account, or a live OpenRouter API.** Engines, streams, wrangler, and compose are faked or dry-run. No secrets in the repo. No personal hostnames; examples use `oc.example.com`.

## Self-host and distribution

This section answers Luke's follow-up. Recommendations are load-bearing (KTDs 4–8); tradeoffs are in the same paragraph as the choice.

### (a) Near one-click Cloudflare

**Recommend:** a Settings control, "Put this online", that runs the same flow as `scripts/setup-cloudflare.sh` (also invokable from the developer install as `--cloudflare`, or alone). The flow: checks `wrangler` and `cloudflared`, runs `wrangler login` (browser), creates or reuses a Tunnel pointing at `http://127.0.0.1:8791`, prints the CNAME the person must add, writes a local Tunnel config, and offers to create an Access application from a template policy (their email as the first allowed identity). Optional flags create an R2 bucket for artifacts (U10) and do *not* create D1 (KTD8). Idempotent: a second run updates rather than duplicates. On the five-click path this is step 4, and is optional — chat already works on localhost after step 3.

Creating the Tunnel and writing its config is not enough: `cloudflared` must actually run. On the five-click path, the Tauri app (or the Python sidecar it already supervises) starts `cloudflared` as a supervised child process once the Tunnel config exists and "Put this online" is on. The supervisor keeps that process running for as long as the app is running and the toggle is on; if `cloudflared` exits unexpectedly, it is restarted with backoff. Startup failures and repeated crash loops are shown in Settings as an error status (reason included), never as a "you're live" state. Turning the toggle off stops the process; quitting the app stops it; opening the app again with the toggle still on starts it again. On the developer path, Settings shows the same status; `cloudflared` is a compose sidecar (or a documented system service if they already run one), not a second unsupervised daemon. The system-service option still targets host loopback (`http://127.0.0.1:8791`), because the host publishes the port there. The compose sidecar does not: inside that container, `127.0.0.1` is the sidecar itself. Its Tunnel target is the opsview Compose service name (`http://opsview:8791`, matching `deploy/server-001/docker-compose.oc.yml` and the localhost compose in U9). That only works if opsview listens on all interfaces inside the container: set `OC_BIND_HOST=0.0.0.0` there, as production compose already does, and keep the **host** publish on `127.0.0.1` only.

**What can be close to one-click:** login, Tunnel create, starting and supervising `cloudflared`, Worker/demo deploy, R2 bucket create, writing local config, printing next DNS and Access steps.

**What cannot:** opening a Cloudflare account, attaching a card, changing nameservers or adding a CNAME at an external DNS host, deciding who is allowed in Access, and trusting a "Deploy to Cloudflare" button to reach a backend that runs on the person's machine. The button is fine for the fixtures-only public demo (`edge/wrangler.jsonc`); it is the wrong offer for the real console.

### (b) Five-click setup (main path) and the developer install

**Recommend the five-click Tauri path as the default for a new person:**

1. Download the desktop app from GitHub Releases (macOS and Linux builds of the Tauri shell; Windows is a later unit, U11, after a portable file lock).
2. Open it. The app starts a bundled Python backend as a single built-in program (a frozen opsview sidecar — PyInstaller or equivalent, shipped next to the Tauri binary) on `127.0.0.1:8791`, then opens the localhost portal in the window. Docker is not required and is not started.
3. Sign in with the existing OpenRouter OAuth (Settings → Connect OpenRouter already does this; use it as the first-run gate).
4. Optionally flip "Put this online" in Settings, which runs the Cloudflare Tunnel and Access flow in (a).
5. Chat.

Data lives in a per-user data directory (`OC_ROOT`), the same files-on-disk model as today. First chat needs no compose file and no wrangler.

**Developers still get a one-command path**, the same image already used on the production host (`deploy/server-001/Dockerfile`). First-run profile is *localhost*: one `opsview` container, `OC_BIND_HOST=0.0.0.0` inside that container (the server defaults to loopback, which a Compose sibling cannot reach), host port published on `127.0.0.1:8791` only, `OC_DURABLE=0`, volume `oc-data`, a generated `.env` from `.env.example` (placeholders only; the script prompts for `OPENROUTER_API_KEY` or leaves Settings → Connect OpenRouter to do it). Optional `--durable` starts Temporal and its Postgres. A VM is "install Docker, run the same compose." Do not ship a second provisioning stack in this wave.

The developer install script is new (`scripts/install.sh`); nothing in the tree is one today (README, `scripts/` has `record_cube.py` and the catalog region check). Document both:

```bash
# from a checkout
docker compose -f deploy/localhost/docker-compose.yml up
```

and a `curl | sh` that clones or pulls the image and runs that compose, with a checksum or a pinned release tag, and a note that piping a script is optional.

### (c) Wrangler CLI

**Recommend it as a step inside (a), not a standalone product.** The script checks for wrangler (corepack / npm), runs `wrangler login`, and uses it for the demo Worker and any R2 creation. Tunnel itself is `cloudflared`. CI tests a dry-run (`--dry-run` prints the wrangler commands and expected config; `ui/scripts/edge-config.test.mjs` already guards the demo Worker against bindings). The person still has to complete the browser login.

### (d) Rust GUI and a web page that sync

**Recommend Tauri wrapping the existing React `ui/`, in this wave, as the main setup path (U5), not a Rust rewrite.** Reusing the SPA stays on one design system (`DESIGN.md`). The window loads the same UI and talks to the bundled opsview on loopback (or, after "Put this online", the Access-protected public URL). A browser on the same machine can use that same URL and the same account session. Sync is that shared API, not a file-sync protocol. If the desktop's local opsview and a browser pointed at a different host are two instances, say so in the UI rather than pretending they merge. Keeping two backends in sync across machines (laptop offline, another host still serving) is a later design — replication and conflict rules — and is not implied by a Tauri window.

### (e) Login and accounts

**Current state:** sign-in is the console gate. Loopback gets `local_session` with identity `local` (a passkey on loopback would prove nothing the local process cannot already bypass). Elsewhere, passkeys (WebAuthn, token-gated enroll) or a session minted from Cloudflare Access's verified email (`access_identity` → `access_session`). `services/accounts` then creates a stable account id (`oc_` + 16 hex of sha256 of the identity) used as the Composio user id, with a display name and sign-out. CSRF is bound to the session; POSTs need Origin + CSRF. Session key prefers omaseal, file fallback (`services/opsview/auth.py`).

**Recommend for self-host:** the five-click path uses the existing OpenRouter OAuth at first run, and the loopback local session for the app itself. Anything published beyond loopback must use Access and/or passkeys; "Put this online" (and the developer setup script) sets `OC_ACCESS_IDENTITY_URL` for the person's team and does not ship a baked default. Do not add email-and-password. The Tauri shell uses the same cookies or a loopback session, not a parallel login.

### (f) DB and storage (files today; SQLite next; D1 no; R2 optional)

**What `main` uses today:** there is **no application SQLite or Postgres**. State is JSON and NDJSON under `OC_ROOT` (default `~/.local/share/oc`, the `oc-data` volume in Docker): `accounts.json`, threads, `orchestrator.ndjson`, `thinking.ndjson`, `openrouter-calls.ndjson`, cost ledger, credentials, session key, artifacts derived from run results (`services/opsview/artifacts.py`). The Postgres service in `deploy/server-001/docker-compose.oc.yml` is **Temporal's database only** (`POSTGRES_DB: temporal`). "R1" and "R2" in `services/execplane/` are **egress conformance rules**, not Cloudflare products — Luke's "r1 r2" is treated here as **D1 and R2**.

| Option | Recommendation |
|---|---|
| Files on the container volume | **Keep for this wave.** Already works, easy to back up (`tar` the volume; `redeploy.sh` already dumps Temporal separately), no extra service for localhost. Weakness: concurrent writers and ad-hoc querying, which localhost single-process does not feel yet. |
| SQLite in the container | **The next app database, when we migrate.** One file on `oc-data`, zero extra containers, good for accounts, sessions, threads, and caps. Talks to the Python backend directly. Migrate behind a compatibility layer; do not dual-write in the first settings PR. |
| Postgres for app data | **No, unless SQLite is proven too small.** A second Postgres next to Temporal's would confuse backups and localhost. Temporal keeps its own. |
| Cloudflare D1 | **No for the app DB.** D1 is for Workers. The backend is Python in a container; putting primary state in D1 adds a network hop, a second consistency story, and a Cloudflare account requirement for localhost. Revisit only if the backend itself moves onto Workers (not this wave; the 2026-11-01 plan also left the backend on the host). |
| Cloudflare R2 | **Yes, optional, for large artifacts and uploads when the person is already on Cloudflare.** Local disk (capped, as today) remains the default. R2 is object storage, not a database. Create the bucket from the setup script; the app uses it only when configured. |

**Clear choice:** localhost and the first self-host keep files on `oc-data`. Plan a SQLite migration as a later PR when a concrete pain appears (U10). Offer R2 as an optional artifact store. Do not introduce D1.

### U1. Stream replies and animate incoming words

- **Goal:** R1, R4, R11. Replies appear as they are written; new words use Reveal.
- **Depends:** none. #160 is on `main` (quiet composer, graphite accent).
- **Files:** `services/openrouter/client.py`; `services/opsview/threads.py`; `services/opsview/server.py`; `ui/src/lib/api.ts`; `ui/src/components/ThreadView.tsx`; `ui/src/components/Reveal.tsx`; `tests/unit/test_openrouter_stream.py`; `tests/opsview/test_thread_stream.py`; `ui` Reveal tests; `tests/e2e/spa.e2e.mjs`. Implements daily-driver U2 rather than a second design.
- **Approach:** `chat_stream` through the official SDK, record one call row with usage at the end (`stream_options.include_usage`). Thread event log + SSE route as in the daily-driver plan. ThreadView appends deltas; Reveal only wraps new tokens. Reduced motion: no animation, no hidden text. If the stream ends without a usage chunk (Stop, disconnect, or a mid-stream error), take the generation id already on the stream and call the existing `GET /generation?id=` helper (`services/openrouter/generation.py` `fetch_generation`). Record that cost on the call row and count it toward the cap. If the lookup fails, record the call with unknown cost and surface it — do not treat the spend as zero. OpenRouter still bills tokens generated before a stop. The cap is fail-closed on that unknown spend: immediately reserve a conservative amount against the cap (`max_tokens`, or the request's output-token limit, times the model's output price — the model served if known, otherwise the one requested). Further paid calls are blocked when remaining cap minus that reservation is insufficient. If a reservation cannot be computed (no price, no token limit), hold all further paid calls until the generation is reconciled. A later successful lookup replaces the reservation with the actual cost and releases any unused portion. Unknown spend is never ignored; the hard cap stays strict.
- **Tests:** scripted chunk lists (no live network); mid-stream error records a failed call and a retryable turn; a stopped or truncated stream with a scripted generation lookup records the billed cost against the call and the cap; a failed lookup leaves cost unknown, not zero, reserves a conservative amount (or holds all further paid calls if a reservation cannot be computed), and blocks a subsequent paid call that would exceed the cap including the reservation; a later successful lookup replaces the reservation with actual cost and unblocks remaining budget; polling fallback matches the final transcript; resume from `Last-Event-ID`; Reveal unit tests for incremental text and `animate=false`; e2e bubble settles; axe; reduced-motion.
- **PR:** `feat/stream-replies-reveal`.

## Risks

- Streaming and reasoning share the OpenRouter client: a careful stream implementation in U1 avoids a rewrite in U2.
- Install-script supply chain (`curl | sh`): mitigate with a pinned tag and a documented compose-only path. The main path is a signed GitHub Release of the Tauri app and its sidecar; still publish checksums, and keep the compose path for people who will not run a downloaded binary.

- Supervised `cloudflared`: a crash loop must surface in Settings, not look live; tests use a fake binary, never a live Tunnel.
- Access identity without a baked default will break a deploy that relied on the implicit team URL — U6 must mention it in the PR and require `OC_ACCESS_IDENTITY_URL` only when Access cookies are present.
- Named agents can multiply spend: caps, depth 1, and spawn metrics are mandatory in U8.
